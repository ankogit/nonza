# Discord-подобный функционал, авторизация, компоненты, расширяемость и оптимизация

## Принципы внедрения (обязательны)

- **Без костылей.** Временные обходы, дублирование логики «только чтобы заработало», хардкод и скрытые зависимости не допускаются. Если для «быстрого фикса» нужен костыль — лучше вынести задачу отдельно и сделать через нормальный контракт (API, слой, интерфейс).
- **Понятная и расширяемая структура.** Слои FSD, shared/meets/rooms, импорты только вниз. Новый экран или фича должны встраиваться в существующие слои без переписывания соседей. Имена и размещение файлов должны однозначно подсказывать, куда смотреть.
- **Если что-то не получается — не спешить, делать дебаг.** Не гадать и не патчить «на авось». Воспроизвести проблему, зафиксировать ожидаемое и фактическое поведение, сузить место сбоя (логи, breakpoints, минимальный пример), поправить причину. При необходимости оставить краткую заметку (в коде или в тикете), почему решение сделано именно так.
- **Результат каждого шага — стабильное состояние.** После реструктуризации — сборка и ключевые сценарии работают. После добавления слоя — импорты и типы проходят. Не накапливать «временно сломанное» в надежде починить потом.

### Общая структура (app-поддомен)

- **Без авторизации:** редирект на экран авторизации (или регистрации).
- **После входа:** корневой layout с **панелью организаций** (снизу или сбоку, как у Slack). Выбранная организация → **экран организации**: сайдбар с комнатами + основная область (комната или пустое состояние / создание комнаты).
- **Отдельные полноэкранные экраны:** авторизация, регистрация, настройки, создание организации, приглашение по ссылке — без панели организаций; после действия возврат в основной layout.

Роутинг: например `/login`, `/register`, `/settings`, `/organizations/new`, `/invite/:token`, `/org/:orgId` (экран организации, сайдбар комнат + контент), `/org/:orgId/room/:roomId` или переход в meet по коду. Для meet-поддомена — только виджет встречи (вход по коду, комната), без панели организаций.

## Часть 1.1. Backend для организаций и приглашений (кратко)

- **Backend:** список организаций — repo `List()` (с фильтром по user при авторизации), **GET** `/api/v1/organizations`. Комнаты по org: **GET** `/api/v1/org/:id/rooms`. Приглашения: модель invite (token, org_id, inviter_id, role, expires_at), **POST** `/api/v1/org/:id/invites`, **GET** `/api/v1/invites/:token`, **POST** `/api/v1/invites/:token/accept` (привязка пользователя к org, например через `organization_members`).
- **Frontend API:** `OrganizationApi.getList()`, `RoomApi.listByOrganizationId(orgId)`, позже `InviteApi.getByToken(token)`, `InviteApi.accept(token)`.
- **Поддомен:** один билд; по hostname (meet vs app) выбирать начальный экран; при app — проверка авторизации и показ layout с панелью организаций.

## Структура фронта: общий слой (shared), meets, rooms — FSD

**Принцип:** одна общая компонентная база, два приложения — **meets** (встречи по коду) и **rooms** (организации и комнаты). В каждом приложении придерживаться **Feature-Sliced Design**: слои app → widgets → features → entities → shared, импорты только «вниз» (в сторону shared).

### Общий слой — `shared/`

Всё, что переиспользуется обоими проектами. Не зависит от meets и rooms.

- **shared/ui** — компоненты: Button, Modal, PixelIcon, PixelSelect, Input, Checkbox, Card, Alert, Spinner, Badge, Divider, Typography, AudioSettings, а также общие ScreenLayout, PageHeader, CardTile, ListEmpty, FormSection, SubmitCancelActions.
- **shared/api** — ApiClient (с поддержкой auth-заголовков), базовые типы запросов/ответов.
- **shared/lib** — утилиты: livekit-helpers, participant-preferences, useDraggablePiP, audio-devices, notification-sounds, constants и т.д.
- **shared/entities** (опционально) — сущности, используемые обоими приложениями: **room** (модель, API: getByShortCode, getToken, create, listByOrganizationId), **organization** (модель, API: getList, getById, create). Либо оставить room и organization в shared, либо дублировать только типы в shared, а API — в каждом приложении по необходимости; предпочтительно единый shared/entities для room и organization, чтобы одна компонентная база.

Стили: **shared/styles** — design.css, main.css, общие переменные и токены. Точка входа стилей для обоих приложений.

### Проект «meets» — `meets/`

Текущий фронт переносится сюда. Сценарий: вход по коду комнаты, виджет встречи (конференц-зал, круглый стол), создание комнаты (опционально), документ, E2EE.

- **meets/app** — точка входа (main.ts), App.vue, роутинг/ветвление по query, NonzaWidget, PreviewMode, UiKitPage. Подключение стилей из shared.
- **meets/widgets** — room-conference-hall, room-round-table, video-participant, create-room-screen, room-created, meeting-document, collaborative-document.
- **meets/features** — room-connection, create-room, e2ee, media-control, participant-replica, conference-hall.
- **meets/entities** — только то, что нужно только meets (например, meeting-document, если не используется в rooms). Room и organization импортируются из **shared/entities**.

Импорты: meets → shared (ui, api, lib, entities). Обратных импортов shared → meets нет.

### Проект «rooms» — `rooms/`

Приложение организаций и комнат: авторизация, регистрация, настройки, панель организаций (как у Slack), экран организации с сайдбаром комнат, создание организации, приглашение по ссылке.

- **rooms/app** — точка входа, App.vue, роутинг (Vue Router или query), layout с панелью организаций, проверка авторизации.
- **rooms/widgets** — экраны: login, register, settings, create-organization, invite-accept, org-panel (панель списка организаций), org-screen (сайдбар комнат + основная область).
- **rooms/features** — auth (логика токена, редирект), create-org, accept-invite, create-room (форма в контексте org) и т.д.
- **rooms/entities** — только rooms-специфичное (например, invite — типы и API приглашений). Room и organization — из **shared/entities**.

Импорты: rooms → shared (ui, api, lib, entities). Для отображения комнаты (вход в встречу) rooms может либо открывать meet-приложение по URL (поддомен meet + code), либо использовать переиспользуемый виджет комнаты из shared (если вынесем комнату в shared/widgets или shared/features); по плану допустимо редирект на meet с кодом комнаты.

### Итоговая схема каталогов

```
apps/meet/src/
  shared/           # общий слой — один на всё
    ui/
    api/
    lib/
    styles/         # design.css, main.css, переменные
    entities/       # room, organization (модели + API)
  meets/            # приложение встреч (текущий фронт)
    app/
    widgets/
    features/
    entities/       # только meet-специфичные (например meeting-document)
  rooms/            # приложение организаций/комнат
    app/
    widgets/
    features/
    entities/       # только rooms-специфичные (например invite)
```

Правила FSD: внутри meets и внутри rooms — слои не импортируют «вверх» (widgets не импортирует из app; features не из widgets; entities не из features). Общий слой shared не знает про meets и rooms. Сборка: два entry point (например `meets/app/main.ts` и `rooms/app/main.ts`) или один с выбором по hostname/env — в плане оставить выбор при внедрении.

## Часть 2. Авторизация

### Цели

- Привязать организации и комнаты к пользователям (владелец организации, участник комнаты).
- Ограничить список организаций / комнат «своими» при включении авторизации.
- Не ломать сценарий «быстрая встреча по коду» без входа (гостевой токен или анонимный участник).

### Варианты

**A. JWT от своего бэкенда (email/пароль или OAuth)**

- Бэкенд: таблица `users` (id, email, password_hash или provider_id), middleware проверки JWT в заголовке `Authorization: Bearer <token>`.
- Логин: POST `/api/v1/auth/login` → выдача JWT (access + опционально refresh). Регистрация: POST `/api/v1/auth/register`.
- Хранение на фронте: в памяти + localStorage/sessionStorage (или только memory для строгой безопасности). ApiClient при каждом запросе подставляет заголовок из хранилища.
- Организации: в `organizations` уже есть `owner_id`; при List фильтровать по `owner_id = current_user_id` (или по таблице членства, если позже появится ролевая модель). Комнаты — без изменений с точки зрения доступа; токен LiveKit по-прежнему по short_code.

**B. Внешний IdP (OAuth2/OIDC)**

- Бэкенд только проверяет JWT от провайдера (например, Keycloak, Auth0, Yandex OAuth). Поле `sub` или `email` — идентификатор пользователя; при первом запросе можно создавать запись в `users` по `sub`.
- Фронт: редирект на IdP, после callback сохраняем access_token (или только id_token) и подставляем в ApiClient. Меньше своей логики паролей.

**C. Гибрид**

- Для «организаций» обязательный вход (JWT/OAuth). Для «встречи по коду» — опционально: если есть токен, подставляем имя/аватар из профиля; если нет — анонимный участник (как сейчас по имени из формы).

### Что заложить в архитектуру сейчас

- **Backend:** единая точка проверки идентичности — middleware `AuthMiddleware` (опциональный: если есть `Authorization` — парсим и кладём `user_id` в контекст; если нет — `user_id = nil`). Роуты организаций и «мои комнаты» вызывают проверку `user_id != nil` и фильтрацию по нему. Роуты токена LiveKit и get room by short_code — без обязательной авторизации.
- **Frontend:** слой «auth» — хранилище токена, метод `getAuthHeaders()` для ApiClient, экран логина/редирект на OAuth. ApiClient расширить: перед каждым запросом вызывать `getAuthHeaders()` и мержить в `headers`. При 401 — очистка токена и редирект на логин (или на meet без авторизации).
- **Модели:** использовать существующий `OwnerID` в Organization; при List — фильтр по текущему пользователю (или по членству в org, когда появится таблица `organization_members`).

Конкретный выбор (свой JWT vs OAuth vs гибрид) можно принять отдельно; важно не размазывать проверку идентичности по хендлерам, а держать её в одном middleware и в сервисах — получать `user_id` из контекста.

## Часть 3. Общие компоненты

### Текущее состояние

- **shared/ui:** Button, Modal, PixelIcon, PixelSelect, Input, Checkbox, Card, Alert, Spinner, Badge, Divider, Typography, AudioSettings и др.
- **shared/api:** ApiClient без авторизации.
- **shared/lib:** утилиты (livekit-helpers, participant-preferences, useDraggablePiP и т.д.).
- Экранные блоки (форма создания комнаты, «комната создана», заголовки, списки) живут в widgets/features и дублируют стили (фон #2a2a2a, бордер 2px solid #444, кнопки primary/secondary).

### Что вынести в общие компоненты

- **Layout / страница**
  - **ScreenLayout** (или **PageLayout**): обёртка `.full-page` с общим фоном и контейнером (max-width, центрирование), слот для контента. Использовать в CreateRoomScreen, RoomCreated, OrganizationsListScreen, OrganizationDetailScreen, CreateOrganizationScreen — чтобы не повторять разметку и классы.
  - **BackLink** (опционально): кнопка «Назад» с единым стилем и поведением (например, переход по истории или по заданному query).
- **Карточки и списки**
  - **CardTile** (или переиспользовать/расширить **Card**): карточка в пиксельном стиле (border, shadow, padding), слоты для заголовка, описания, действий. Использовать для организаций в списке и для комнат на странице организации (и при желании для room-type в CreateRoomForm).
  - **ListEmpty**: блок «список пуст» + опциональная кнопка действия (например, «Создать организацию»). Использовать в OrganizationsListScreen и в списке комнат.
- **Формы**
  - Общие стили форм уже заданы в CreateRoomForm; можно вынести в **shared/ui** компонент **FormSection** (label + hint + слот) и кнопки **SubmitCancelActions** (две кнопки в одном стиле), чтобы CreateOrganizationForm и будущие формы их переиспользовали.
  - Не обязательно дробить сам CreateRoomForm на мелкие кусочки — достаточно, чтобы новые экраны (CreateOrganization, настройки и т.д.) использовали те же FormSection/SubmitCancelActions и тот же набор инпутов из shared/ui.
- **Заголовки страниц**
  - **PageHeader**: заголовок страницы (title + опционально subtitle, опционально action-slot справа). Единый стиль для «Организации», «Название организации», «Создать организацию».

Итог: общие примитивы уже есть (Button, Input, PixelIcon); добавляем уровень «страница и список» (ScreenLayout, CardTile, ListEmpty, PageHeader, FormSection/SubmitCancelActions), чтобы экраны организаций и будущие разделы собирались без копирования вёрстки.

## Часть 4. Расширяемость

### Роутинг

- Сейчас: один App.vue, ветвление по query (`page`, `id`, `action`). Для роста числа страниц возможны два пути:
  - **Вариант 1.** Оставаться на query и вынести маппинг в один модуль: `getRouteFromSearchParams(search)` возвращает `{ page, params }`, App.vue рендерит по `page`. Новые страницы = новая ветка в маппинге и новый компонент.
  - **Вариант 2.** Ввести Vue Router с history mode и маршрутами вида `/organizations`, `/organizations/new`, `/organizations/:id`, `/` (meet). Один базовый layout, дочерние роуты для организаций и для meet. Поддомен по-прежнему может переключать начальный маршрут.

Рекомендация: при появлении 5+ «страниц» перейти на Vue Router; до того — достаточно централизованного парсинга query в одном месте.

### Модули и фичи

- **Структура по слоям:** entities (модели + API), features (логика + UI одной фичи), widgets (сборка экранов из features и entities), app (роутинг, глобальное состояние, провайдеры). Новый сценарий (например, «календарь встреч») — новый feature или widget, подключаемый в app через роут или флаг.
- **Feature flags / режимы:** переменная окружения или конфиг (например, `VITE_ENABLE_ORGANIZATIONS`) для включения пункта меню «Организации» и роутов. Позволяет собирать «лёгкий» билд только для встреч без организаций.
- **Поддомены:** логика «meet vs app» по hostname остаётся в app-слое; остальной код не должен завязываться на домен, только на «текущий режим» (meet / org), передаваемый пропсом или через provide/inject.

### Backend

- Новые сущности — отдельный пакет в `internal/models`, свой репозиторий, сервис, хендлер; роуты регистрируются в handler.go. Авторизация — только через общий middleware и `user_id` в контексте.
- При появлении ролей (member, admin, owner) — таблица `organization_members` и проверки в сервисе организаций/комнат, без дублирования логики в каждом хендлере.

## Часть 5. Оптимизация

### Загрузка и бандл

- **Lazy-load экранов:** страницы организаций (OrganizationsListScreen, OrganizationDetailScreen, CreateOrganizationScreen) и, при желании, CreateRoomScreen и RoomCreated — подключать через `defineAsyncComponent` или `() => import(...)` в месте ветвления в App.vue (или в роутере). Тогда начальная загрузка meet-виджета не тащит код списка организаций.
- **Разделение по поддомену (опционально):** при hostname = meet не подгружать чанки организаций (проверка в месте импорта или отдельная точка входа для meet). Требует аккуратной настройки (например, два entry или условный динамический import по hostname).
- **Общие чанки:** shared/ui и shared/lib при использовании из нескольких lazy-страниц собьются в общие chunk’и автоматически при правильных импортах.

### Рендер и состояние

- В комнатах (RoomConferenceHall, RoomRoundTable) уже используются приёмы из правил проекта: v-memo по срезу зависимостей, стабильные ключи в v-for. Для списков организаций и комнат: ключ по `org.id` / `room.id`; при отображении больших списков можно добавить виртуализацию (например, vue-virtual-scroller) только при появлении десятков/сотен элементов.
- Списки организаций и комнат — загрузка по требованию (при открытии страницы), без предзагрузки всех данных на старте приложения. Кэширование в памяти (например, список организаций после первого захода на `?page=organizations`) — опционально, при необходимости инвалидация после создания/удаления.

### API и сеть

- ApiClient уже с timeout; при авторизации один раз вешать заголовок из хранилища — без лишних запросов. Список комнат — один запрос GET при открытии страницы организации; не опрашивать периодически, если не нужен real-time (при появлении real-time — WebSocket или polling по решению).
- Токен LiveKit и подключение к комнате — без изменений; тяжёлая часть уже в существующей логике.

## Валидация плана: что не учли и что решить

### Сборка и деплой

- **Два сценария сборки сейчас:** (1) lib — виджет для встраивания на сторонние сайты (`src/index.ts` → NonzaWidget); (2) app — SPA для разработки/деплоя (`vite.app.config.ts`). После реструктуризации (shared, meets, rooms) нужно явно зафиксировать: lib остаётся (entry = meets-виджет из shared + meets) или только два SPA (meet + app)? Как nginx раздаёт meet vs app — один index.html с роутингом по hostname или два артефакта с разными путями?
- **Env при двух entry:** VITE_API_BASE_URL, VITE_LIVEKIT_URL — общие для meet и app (один бэкенд). При двух отдельных билдах — один .env в корне фронта; при одном билде с hostname-роутингом — то же. Явно добавить в шаг «настройка сборки»: перечень env и где они читаются (shared vs meets vs rooms).

### Backend и данные

- **Таблица organization_members:** приглашение «принять в организацию» предполагает, что пользователь после accept становится членом организации. Сейчас в модели только `owner_id`. Нужна таблица членства (organization_members: user_id, organization_id, role) **до** или **вместе с** приглашениями; accept приглашения добавляет запись в organization_members. В порядок внедрения добавить явно: сначала модель членства + миграция, потом invites.
- **Минимальные права:** кто может создавать комнаты в организации (только owner или и участники)? Кто может приглашать? Зафиксировать в одну строку в плане: например «MVP: создание комнат и приглашения — только владелец org».
- **Миграции:** новые таблицы (users, organization_members, invites) — через GORM AutoMigrate или отдельные миграции с версиями и откатом? В плане не указано; при внедрении не забыть порядок применения.

### Авторизация и поддомены

- **Общий домен для cookie/token:** если meet.nonza.ru и app.nonza.ru — разные поддомены, то localStorage изолирован по поддомену. Чтобы «залогинен на app» означало «залогинен и на meet», либо cookie с domain=.nonza.ru, либо один домен (например app.nonza.ru с путями /meet и /org). В плане зафиксировать выбор при внедрении поддоменов.
- **Refresh token и истечение:** план упоминает access (и опционально refresh), но не поведение при истечении access (тихий refresh по refresh_token vs редирект на логин). Решить в рамках «авторизация».

### Ошибки и граничные случаи

- **API недоступен / нет сети:** что показываем пользователю (экран ошибки, повтор запроса, тост)? Не описано в экранах.
- **Истёкший invite token:** экран «приглашение истекло» + кнопка «Закрыть» или «На главную».
- **Повторный accept по той же ссылке:** пользователь уже в организации — идемпотентный ответ (успех) или сообщение «Вы уже в этой организации». Решить на бэкенде и отобразить на фронте.
- **Пустой список организаций после входа:** призыв «Создать первую организацию» или «Принять приглашение по ссылке» — уже заложено в панель организаций, но явно не сформулировано как edge case.

### Навигация между meet и rooms

- **Вход в комнату из rooms:** «переход в комнату по short_code» — редирект в той же вкладке на meet.nonza.ru?code=xxx (тогда в rooms размонтируется всё и загружается meet) или открытие meet в новой вкладке? Или встраивание виджета комнаты (из shared) внутрь rooms? План даёт варианты; при внедрении зафиксировать один вариант, чтобы не разъехаться (рекомендация: редирект в той же вкладке на meet с code).
- **Кнопка «Создать комнату» в meets:** после появления rooms создание комнаты — в rooms (в контексте org). В meets оставлять ли кнопку «Создать комнату» и вести на app, или убрать из meets и оставить только «Войти по коду»? Зафиксировать в плане.

### Контракты и типы

- **Валидация ответов API:** типы Room, Organization на фронте — доверяем бэкенду или парсим/валидируем (например zod)? Не учтено; для расширяемости можно отметить «при желании — валидация в shared/entities при получении с API».
- **Пагинация:** GET /organizations и GET /org/:id/rooms — в MVP отдаём все записи. При росте — пагинация (cursor/limit) или бесконечный скролл; в плане отметить «вне scope MVP, при необходимости добавить».

### Тестирование и качество

- **Тесты:** план не требует unit/e2e для новых экранов и реструктуризации. Имеет смысл зафиксировать: «критичные сценарии (логин, создание org, вход в комнату по коду) — при возможности покрыть e2e или ручной чек-лист» или «тесты — по решению команды после стабилизации».

### CORS

- **Поддомены в CORS:** при деплое meet.nonza.ru и app.nonza.ru оба origin должны быть в CORS_ALLOWED_ORIGINS на бэкенде. Упомянуто в тексте плана; при деплое не забыть добавить оба в конфиг.
